# Pinned PostgreSQL 16 grammar inventory

This directory fixes the full upstream grammar denominator for further work.
It does **not** claim that SQLean currently parses every production, validates
every statement, or preserves every statement's execution semantics.

The official `postgres/postgres` revision is
[`f0595c3d839debdb140903621c1b44a4f4d86256`](https://github.com/postgres/postgres/tree/f0595c3d839debdb140903621c1b44a4f4d86256),
selected from `REL_16_STABLE`. Its vendored `configure.ac` identifies
**PostgreSQL 16.15**. This matches the major version of the project's native
PostgreSQL tests; it is independent of the PostgreSQL 17 raw-parser oracle
used in earlier corpus audits.

[sources.json](sources.json) records SHA-256 digests, byte lengths, and
commit-specific download URLs for six unmodified files:

- `gram.y`: Bison grammar, precedence declarations, and embedded C actions.
- `scan.l`: core lexer patterns and actions.
- `parser.c`: raw-parser entry modes, lookahead-token rewriting, and Unicode
  token processing.
- `kwlist.h`: keyword token/category/bare-label definitions.
- `configure.ac`: pinned upstream version evidence.
- `COPYRIGHT`: the upstream PostgreSQL license and attribution.

The source files retain their upstream headers and PostgreSQL licensing.
The inventory script does not execute SQL, compile the upstream C files,
run their semantic actions, or execute an upstream build/configure script.

## Inventory and reproduction

[inventory.json](inventory.json) is generated by **GNU Bison 3.8.2** XML
reports, not by splitting the grammar with regular expressions. Bison handles
strings, comments, nested C action bodies, precedence, and empty rules.
The keyword reader separately tokenizes C strings/comments before reading
`PG_KEYWORD` macros.

The pinned inventory contains:

- **3,284 source productions**, plus Bison's generated acceptance production.
- **705 source nonterminals**, plus `$accept`.
- **518 Bison-reported terminals** and **471 keyword entries**. The terminal
  count includes punctuation, special tokens, EOF, and parser-internal modes;
  it is not a count of SQL keywords.
- **6,223 LALR states** and **1,454 resolved precedence conflicts**.
- **125 statement-family entry points**: 124 nonempty alternatives of `stmt`,
  plus `TransactionStmtLegacy` under `toplevel_stmt`.

The report also retains all six `parse_toplevel` entry modes. Only the default
mode starts with an ordinary statement list; the remaining modes parse a type
name or PL/pgSQL expression/assignment fragments. Statement-family counts are
grammar entry points, not counts of distinct SQL command spellings.

From the repository root, with Bison 3.8.2 installed:

```sh
python3 scripts/inventory_postgresql_grammar.py --check
python3 scripts/test_postgresql_grammar_inventory.py
python3 scripts/generate_postgresql_grammar.py --check
python3 scripts/test_postgresql_grammar_generation.py
```

Both commands are offline. Regenerate `inventory.json` by omitting `--check`.
The explicit `--download` option restores only files matching the committed
source hashes at the pinned URLs. A changed hash, version, source inventory,
keyword category, or unreviewed statement-family partition fails the check.
XML and generated C reports are temporary files and are removed afterward.

The regression suite mutates source bytes, metadata, keyword declarations,
XML symbol references, and real grammar alternatives. It also inserts
grammar-like text inside comments, strings, nested C actions, and the C
epilogue, verifying that these do not invent grammar productions. Bison may
introduce explicit midrule-action nonterminals in synthetic test grammars;
the reader retains those correctly. This pinned PostgreSQL grammar has none.

## Current coverage annotations

The manifest labels eight existing AST families **partial**: SELECT,
INSERT, UPDATE, DELETE, restricted CREATE TABLE, selected ALTER TABLE actions,
table-only DROP, and table/column renaming. The other 117 entry points are
marked **not implemented** by the production AST interface. No family is
labeled complete. These are reviewed interface annotations, not measured
production coverage or a percentage of PostgreSQL compatibility.

The remaining grammar includes general functions and special forms,
conditional expressions, arrays and rows, windows and ordered-set aggregates,
locking, additional pagination forms, qualified/custom types, table functions,
XML, MERGE, complete mutation clauses, and the broader object/session/utility
language. `feature_gaps` names representative grammar roots without claiming
that a short feature list replaces the complete production inventory.

The independent SELECT validity rules and checked rendering profiles continue
to define their own, smaller assurance domains. A family-level syntax
annotation does not add constructors or theorems to either contract.

## Independent grammar-recognition layer

`SQLean/PostgresGrammar` provides a separate syntax layer. Generated Lean data
contains all 6,223 action/goto states and 3,285 production entries, including
the generated acceptance rule. The interpreter is total and bounds shifts
and reductions with explicit fuel, returning inconclusive on exhaustion.
Shared shift rows reduce 432,653 expanded transitions to 76,118 stored
entries across 1,794 distinct rows. The generator checks that every original
transition is retained. [lean_generation.json](lean_generation.json) records
hashes of all 82 generated modules.

The independent inductive `Derives`/`DerivesList` judgments justify reductions:
the chosen production belongs to the fixed grammar, its children derive the
right-hand side in order, and their token sequences concatenate to the
parent's sequence. `parseTokens` returns a `Certificate` deriving
`parse_toplevel` over exactly the complete supplied token stream. Caller
tokens exclude EOF; the interpreter's private sentinel is excluded from the
certificate. Token payload strings and offsets are retained exactly but are
opaque to this grammar judgment.

This establishes **grammar-derivation soundness** without defining validity
as checker success. The independent specification imports only grammar
syntax, not the LR interpreter or tables. Even incorrect LR choices cannot
produce an invalid derivation: successful reductions check production
membership, child symbols, and ordered token concatenation, while acceptance
checks the exact full input. Completeness, the intended precedence tree, and
equivalence to PostgreSQL's parser remain separate obligations.

The 45 Lean regressions include a constructive derivation independent of the
interpreter, malformed-table and token rejection, exhausted fuel, 30 varied
PostgreSQL token streams, and five malformed streams. The generator suite
compares every XML shift, goto, enabled reduction, explicit error, and default
action, and rejects altered IDs, targets, symbol roles, and conflicting
actions. These are finite tests, not a universal equivalence proof for Bison
or its generator. `parseTokens_sound` uses Lean's standard `propext`; it adds
no custom axioms, proof placeholders, or native proof-evaluation shortcuts.

Several additional boundaries are essential:

1. `scan.l` and `parser.c` must be modeled, including lookahead rewrites such as
   NOT/NULLS/WITH/WITHOUT, Unicode identifiers/strings and UESCAPE, comments,
   operators, and literal forms. A token-stream theorem alone is not a theorem
   about arbitrary SQL source text.
2. PostgreSQL grammar actions perform checks and transformations beyond the
   context-free rules. For example, `CreateAssertionStmt` is a grammar
   alternative whose C action reports unsupported functionality. A grammar
   tree for that production is not evidence that PostgreSQL accepts it.
3. Raw grammar recognition does not establish catalog binding, exact types,
   clause semantics, privileges, transaction execution, or renderer correctness.
   Generic grammar trees must remain distinct from the existing typed SQL AST
   and independent validity certificates.
4. Lexer fidelity, action-level restrictions, translation into the typed AST,
   complete independent validity, and execution-preserving rendering must each
   be tracked explicitly. They cannot be inferred from a complete LR table.

PostgreSQL itself separates raw parsing from semantic transformation; see the
[PostgreSQL 16 parser-stage documentation](https://www.postgresql.org/docs/16/parser-stage.html).

## Synthetic witnesses and CLI corpus checks

`synthetic.json` contains **6,156** deterministic grammar-derived statements
covering all **125** outer statement families. The generator expands complete
family alternatives and bounded subtree alternatives from the pinned inventory;
it does not execute the resulting SQL. Identifiers, literal values, and
parameters have ordinary source spellings. `synthetic_inventory.json` reports
**6,107 structural templates** separately from statement count.

**123 families reach the requested 50 examples.** `CheckPointStmt` has only
`CHECKPOINT` and contributes one example; `DiscardStmt` has five spellings and
contributes five. Their shortfalls of 49 and 45 remain explicit. The generator
does not pad counts with changed keyword casing, whitespace, or comments.
These examples establish finite grammar coverage, not static validity.
In particular, the `CreateAssertionStmt` examples demonstrate the stated
boundary: their grammar is derivable even though PostgreSQL's C action rejects
that feature.

The offline generator and CLI checks are:

```sh
python3 scripts/generate_postgresql_grammar_examples.py --check
python3 scripts/test_postgresql_grammar_cli.py
python3 scripts/check_postgresql_grammar_cli.py \
  --report-json .lake/postgresql-grammar-cli.json
```

The CLI runner uses `.lake/build/bin/sqlean_pg_grammar --jsonl`. It replays
**10,609 corpus records**: the 6,156 synthetic examples, all 276 earlier external
audit statements, 50 unchanged examples each for functions, conditionals,
pagination, extended types, and row locking, and the statement corpus's 3,924 unchanged
positive examples plus three PostgreSQL-version boundary negatives.
There are **10,606 accepted records and three expected rejections**; repeated
SQL across corpora remains separate provenance evidence and the report also
records the distinct-SQL count.

All 125 outer families and **2,371 distinct reduction productions** are observed.
That production count is finite test coverage, not a proof that every production,
combination, or PostgreSQL semantic action is covered. The
[statement-family corpus inventory](../statement_families/inventory.json)
retains its own per-family concrete-source shortfalls rather than replacing
them with synthetic cases.

The additional **44 protocol checks** cover UTF-8 byte offsets, exact source
preservation through stdin/file/argument and JSONL interfaces, CRLF, comments,
string continuation, Unicode escapes, contextual tokens, invalid requests,
malformed SQL, and an inconclusive zero-transition budget. Every accepted token
must match its exact source byte slice; every gap must independently contain
only PostgreSQL whitespace or nested/line comments. A strict report validator
rejects malformed IDs, unknown productions/families, changed assurance fields,
duplicate JSON keys, extra output, and incorrect process exit codes. Its
**27 offline mutation tests** exercise those rejection paths and the explicit
synthetic shortfalls.

No SQL in this runner is submitted to a database. JSON describes the result of
an in-process Lean certificate construction, not a portable serialized proof.
The optional report records input hashes and the executable hash; C semantic
actions, SQL catalog/type validity, and execution-preserving rendering remain
separate obligations.
